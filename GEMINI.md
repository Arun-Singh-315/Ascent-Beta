# Gemini AI Assistant Rules for Ascent

1. **Branching & Lifecycle**: Always develop on a feature branch (`feature/<name>`). Never commit unverified changes directly to `main`. When a feature or set of fixes is verified and completed with all tests passing, merge the feature branch cleanly into `main`, checkout `main`, and create a new feature branch (`feature/<name>`) for the next task.
2. **Performance First**: Keep the Home screen lightning fast (<100ms render). No continuous GPS listeners, no heavy fluid animation loops, no multi-stream lag on Home.
3. **UI / UX**: Translucent glass containers with subtle 1px border. Deep soothing background. Tactile haptics on every interaction.
4. **AI Gateway**: Keep AI interaction centralized in the AI Assistant button (dynamically reflecting the configured assistant identity name, defaulting to Riya) linking to `/ai-assistant`.
5. **Back Button**: Double-tap back on Home to exit, and back from other tabs reverts to Home tab first.
6. **Deployment & Merge**: Merge verified feature branches into `main`. Compile APK and install on device via ADB when requested.
7. **Preview Capping & Scalability**: Dashboard and Home preview lists (e.g. Today activities) must never grow unbounded or fill the full screen. Always cap preview items (e.g., max 4) with explicit "Show more / Show less" and "View all / Open board" navigation.
8. **CRUD Completeness & Cascading Deletion**: Any created entity (activities, tasks, reminders, routines) must provide full, intuitive Edit and Delete capabilities. Deleting an item must cascade cleanly across the entire system — removing associated reminders, scheduled notifications, running timers, and database references without leaving orphan reminders or notifications behind.
9. **Activity Classification Integrity**:
   - Simple **To-do** items (without an estimated target duration) must NOT have a focus timer clock or play button; they only offer completion toggles and edit/delete options.
   - **Timed / Duration** activities have dedicated countdown/stopwatch controls and focus timer sessions.
10. **Design Preservation Principle**: Visual redesigns and aesthetic enhancements must NEVER eliminate, obscure, or orphan existing functional entry points (e.g., Course Catalog switcher, syllabus viewer, or player sheets). All navigation flows must remain explicit, intuitive, and fully accessible.
11. **Feature Deprecation & Thorough Code Purging (No Dead Code)**: When any feature or module is removed or replaced, perform an end-to-end clean purge across the entire codebase. Completely eliminate associated screens, widgets, routes, DAOs, table definitions, providers, mock data seeders, and unused assets. Never leave behind dead code, unused imports, zombie references, or commented-out ghosts. Accompany every removal with comprehensive test updates to keep the test suite 100% clean and passing.
12. **Test-Driven Development (TDD) & Pre-Approval Verification**: For any new feature, architectural enhancement, or bug fix, comprehensive unit and integration test cases MUST be authored first to specify all requirements, edge cases, and lifecycles. Features and code changes are only considered complete and eligible for approval or merge once all test cases pass with 100% green status.
13. **UI Overflow Immunity & Accessibility Safeguard**: Every screen, card, header, and dialog MUST be tested and verified at **320px width** with **2.0x accessibility text scale** (`TextScaler.linear(2.0)`). Zero `RenderFlex` overflows permitted anywhere in the app. Dynamic text and multi-element rows must employ `Expanded`, `Flexible`, `FittedBox(fit: BoxFit.scaleDown)`, or `Wrap` with defensive spacing.
14. **Interactive Completeness & Non-Blocking User Journeys**: Never create "dead-end" cards, dummy tiles, or non-functional visual shells. Every rendered entity (card, metric tile, preview item, badge) must feature an active, intuitive user journey (tap navigation, sheet launcher, detail view, or action menu). If an item or card is created, the user journey to view, edit, action, and delete it must be complete and unblocked before merging.
15. **High-Volume & Boundary Protection**: All lists, tables, and collections must gracefully handle empty states (0 items), standard states (1-10 items), and boundary stress states (100+ items) without visual distortion, memory leaks, or UI thread freezing. Dashboard and preview lists must enforce strict preview caps (e.g., max 4) with explicit "Show more / View all" pagination to prevent viewport blowouts.
16. **Centralized Token Discipline (Zero Magic Values)**: Hardcoded inline colors (`Color(0x...)`), arbitrary padding numbers, and ad-hoc corner radii are strictly forbidden in UI screens and feature components. All styling must resolve strictly through `AscentTheme`, `context.glass`, `AscentDimensions` (e.g. `AppSpace`, `AppGeometry`), `color_tokens.dart`, or `app_constants.dart`.


17. **Temporary Planning Documents**: Implementation plans and task-specific planning documents are temporary working files. Delete them after implementation and verification are complete. Do not commit or retain a planning document as a deliverable unless the user explicitly asks to keep it. Preserve maintained product documentation and repository rules.
18. **Home Section Heading Consistency & Visual Lineage**: Every major section heading placed on the Home screen (e.g. Life & Health, Things Hub, Mind Palace, Vault/Locker, or other home section headers) must strictly inherit and match the canonical typography token, font size, weight, and styling established by existing Home headings (`AscentTextStyles.homeTitle.copyWith(color: g.ink, fontSize: 20, fontWeight: FontWeight.w700)`). Never introduce arbitrary text sizes or discordant header styles. When adding any new section on Home, always inspect existing established headings (such as "Life & Health") and reproduce their exact styling and layout hierarchy.
